最终判断

先装 telescope-undo 与 nvim-scissors

这两个插件净收益最高。前者把不可见的 undo tree 变成可搜索的历史数据；后者直接复用现有 LuaSnip 与自定义 snippets。稳定使用一周后，再考虑 live-rename 与 actions-preview。不要一次性装满评分榜。

第一梯队：真正新增能力

这些插件能复用你已有的 Telescope、LuaSnip、LSP 或 nui.nvim，没有制造第二套文件树、picker、Git 或诊断入口。

01 · RECOVERY

telescope-undo.nvim

93

把当前 buffer 的撤销树变成可搜索、可预览的时间线，不再靠连续按 u 猜历史。

应用场景
误删后比较多个历史节点；只捞回某次修改中的部分文本。
现有协同
直接复用 Telescope 与 Plenary。
风险
低；不改核心编辑语义。
建议第一批安装 788 stars
02 · SNIPPET MAINTENANCE

nvim-scissors

91

在 Neovim 内创建、编辑、删除 VSCode 格式 snippet，提供语法高亮、转换和热加载。

应用场景
维护 Go、Lua、Markdown 模板，不再手改 JSON/Lua。
现有协同
你已有 LuaSnip 与自定义 snippets。
风险
低；要求 Neovim 0.12，当前已满足。
建议第一批安装 582 stars
03 · SAFE REFACTOR

live-rename.nvim

88

在真正执行 LSP rename 前，用 extmark 实时显示跨文件改名结果。

应用场景
重命名公共符号、接口或字段，先确认影响面再落盘。
现有协同
替换裸 vim.lsp.buf.rename，不新建 LSP 层。
风险
低；但应先验证复杂 workspace edit。
第二批安装 127 stars
04 · CODE ACTION SAFETY

actions-preview.nvim

82

选择 LSP Code Action 前显示 diff，避免执行自动导入或 quick fix 后才发现改错。

应用场景
多个修复候选、自动导入、结构化重构。
现有协同
可以直接使用现有 Telescope 与 nui.nvim。
风险
低；收益取决于语言服务器提供的 action 质量。
第二批安装 517 stars

最小安装顺序

一次只引入能独立验证的能力。插件稳定不等于组合稳定，尤其是键位和事件回调。

第 1 周只装 telescope-undo。观察是否真的替代盲目 undo。
第 2 周加入 nvim-scissors，迁移 2–3 个常用 snippet 验证维护收益。
第 3 周加入 live-rename 与 actions-preview，验证 Go/Lua LSP 行为。
之后multicursor 与 yanky 每次只试一个，避免同时改写编辑肌肉记忆。
退出标准：连续两周每周使用少于两次，或者已有插件能更简单完成同一件事，就删除。不要为“以后可能用”维护配置。

旧报告结论如何变化

Kulala 与 Sidekick 已从“版本阻塞候选”变成已安装基线。本机已经升级到 Neovim 0.12.5，因此旧报告中关于 0.11.1 的判断不再成立。
multicursor 与 yanky 仍然值得试，但优先级下调。它们改动编辑肌肉记忆；telescope-undo 与 nvim-scissors 更容易独立验证，也更贴合当前配置。
Oil、CodeDiff、quicker 仍然只能作为替换方案。不要在 Neo-tree、Diffview、Trouble 旁边叠第二套入口。
